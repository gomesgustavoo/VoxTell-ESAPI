Install VoxTell in Eclipse

For Eclipse administrators and medical physicists · RTM 16.1 · .NET Framework 4.6.2

VoxTell is an ESAPI script — two managed DLLs on your published-scripts share. There is nothing to install on a server and no database to provision. The whole procedure is a file copy and a script approval, and the order below matters.

No published build yet. The 2.0.2.0 release is being prepared. Until it is signed and its SHA‑256 recorded, this page deliberately does not offer a download — Eclipse approves a script by version and content hash, and handing a site bytes whose hash is not published is how a clinic ends up trusting a binary nobody can verify. Ask us for the current build if you need it now.

1. Get the files

A release is a single zip containing exactly two files — the VoxTell interface assembly and Newtonsoft.Json.dll. It contains no Varian assemblies (they are not redistributable), no .pdb, and no XML doc files.

2. Verify what you were given

Before copying anything to a clinical share, confirm the bytes match the published hash. In PowerShell on the workstation: 

Get-FileHash .\VoxTell-Interface.zip -Algorithm SHA256

Compare the result to the value published on this page and in releases.json. If they differ, stop — do not approve it.

3. Copy both DLLs to the published-scripts share

\\<your-VA_DATA-server>\VA_DATA$\ProgramData\Vision\PublishedScripts\

Both files go in that directory. Newtonsoft.Json.dll is not optional: the plugin fails to load without it, and the error Eclipse shows names the assembly rather than the cause.

4. Approve the script — read this part twice

  1. Approval is per version and per content hash

    Eclipse records both. Any rebuild — even a one-character change — produces different bytes and must be re-approved on every workstation. There is no way to inherit approval across builds.

  2. Never ship a hotfix under an existing version number

    If the AssemblyVersion stays the same while the bytes change, Eclipse rejects the script outright with "the script has been modifed" (sic). Every published build gets a new version.

  3. Approve for write access

    Read-only approval loads the panel and lets you sign in, then fails when it tries to create structures. The plugin needs write approval to add anything to a structure set.

  4. The plugin never saves — you do

    VoxTell opens a modification session and writes structures into the open plan. It does not call save. Nothing reaches the patient record until you save in Eclipse, and discarding the session discards every contour it added.

5. Allow outbound HTTPS to both hostnames

  • voxtell.dicomsegvr.com — sign-in, job control, results
  • s3.dicomsegvr.com — the image upload itself

A firewall that allows only the first is the most common failure. Sign-in succeeds, the job is created, and then the upload hangs with no useful error, because the voxel data goes straight to object storage rather than through the API.

6. Sign in

Two options, and either works: sign in from the plugin itself — it opens your browser and listens on loopback ports 47653–47655, falling back to a device code if those are blocked — or paste a workstation key created in the dashboard. Mint one key per workstation so a single machine can be revoked without disturbing the others.

7. If a hostname will not resolve

Windows caches negative DNS answers for about 15 minutes, so a lookup that failed once keeps failing even after the firewall is opened. Flush it: 

ipconfig /flushdns

This is the fix behind the plugin's own "could not resolve host" message, and it is worth trying before investigating anything else.

What to expect the first time

Open a plan, launch VoxTell, type a structure name, and submit. The image series uploads once; every further prompt on the same series moves no image data at all. A typical structure set comes back in seconds to a couple of minutes depending on queue depth, and the contours appear in the open plan ready for review.
